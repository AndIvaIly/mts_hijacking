# ТЗ по ролям: ИИ-консультант МТС Energytool

Nov 11, 2026 · @Ivan

## Как устроено решение

Одно Python-ядро консультанта работает в двух местах: в `solution.py` для автопроверки и в API-сервере для веб-чата. Так лидерборд (50% онлайн-этапа) и демо для экспертов показывают одно и то же поведение, а логика не дублируется.

| Компонент | Владелец | Что делает | Технологии |
| --- | --- | --- | --- |
| Ядро консультанта `core/` | Иван | Поиск по базе знаний, выбор действия, генерация ответа, резюме заявки | Python, bge-m3, BM25, Qwen |
| `solution.py` | Иван | Точка входа автопроверки: вызывает ядро без сервера и без БД | Python |
| API-сервер `server/` | Арчи | Сессии, история, заявки, вызов ядра | FastAPI, SQLite |
| Веб-чат `web/` | Андрей | Чат, режим отладки, история сессий, режим виджета | React, Vite, TypeScript |
| Инфраструктура | Арчи | Docker, compose, деплой, README, сборка архива сабмита | Docker Compose |

Путь одного сообщения:

1. Веб-чат отправляет текст пользователя на API-сервер.
2. Сервер достаёт историю сессии из БД и передаёт её ядру.
3. Ядро ищет фрагменты в базе знаний, выбирает действие и генерирует ответ.
4. Сервер сохраняет ответ вместе с отладочными данными и возвращает его чату.
5. Если ядро вернуло готовую заявку, сервер сохраняет её отдельной записью.

Допущения, на которых построено ТЗ (команда их ещё не утверждала):

- **Python на бэкенде.** `solution.py` и `requirements.txt` заданы организаторами на Python; второй язык означал бы две реализации логики.
- **SQLite вместо Postgres.** Реальные интеграции не требуются, а один файл в Docker-томе проще поднять одной командой.
- **Без векторной БД.** Предполагаю, что база знаний небольшая и индекс помещается в память; если документов тысячи, решение пересматриваем.
- **Этапы без дат.** Дедлайн онлайн-этапа в ТЗ не указан, поэтому порядок работ дан этапами.

## Контракты между участниками

Три контракта ниже фиксируются в конце этапа 1 и после этого меняются только с согласия всех троих. Пока они стабильны, каждый работает независимо: Андрей на моках, Арчи на заглушке ядра.

### Контракт 1. Функция ядра (Иван → Арчи)

```python
def answer(messages: list[dict], debug: bool = False) -> dict:
    """messages: [{"role": "user" | "assistant", "content": str}, ...]
    Последний элемент всегда реплика пользователя. Функция без состояния."""
```

Результат:

```json
{
  "answer": "текст ответа бота",
  "action": "answer",
  "sources": [
    {"doc_id": "kb-012", "title": "Название документа", "snippet": "фрагмент до 300 символов", "score": 0.83}
  ],
  "lead": null,
  "debug": {
    "search_query": "переписанный поисковый запрос",
    "timings_ms": {"rewrite": 0, "retrieval": 40, "rerank": 180, "llm": 1900, "total": 2120}
  }
}
```

### Значения поля action

| action | Когда | Что делает интерфейс |
| --- | --- | --- |
| `answer` | Ответ найден в базе знаний | Показывает ответ |
| `clarify` | Запрос неясен или найденного недостаточно | Показывает уточняющий вопрос |
| `out_of_scope` | Вопрос вне базы знаний или вне продуктов Energytool | Показывает ответ и кнопку «Связаться с менеджером» |
| `offer_lead` | Ответ дан, и момент подходит для заявки | Показывает ответ и кнопку «Связаться с менеджером» |
| `collect_lead` | Бот собирает ФИО, телефон, компанию | Показывает вопрос бота, отмечает собранные поля |
| `lead_ready` | Все три поля собраны, резюме сформировано | Показывает карточку заявки с резюме |

Поле `lead` заполняется при `collect_lead` (частично) и `lead_ready` (полностью):

```json
{"full_name": "Иванов Иван Иванович", "phone": "+79990000000", "company": "ООО Ромашка", "summary": {}}
```

### Контракт 2. HTTP API (Арчи → Андрей)

| Метод и путь | Назначение | Ответ |
| --- | --- | --- |
| `POST /api/sessions` | Создать новый диалог | `{session_id}` |
| `POST /api/sessions/{id}/messages` | Отправить реплику `{text}` | Результат ядра плюс `message_id` |
| `GET /api/sessions` | Список всех сессий, включая без заявки | `[{session_id, started_at, messages_count, has_lead, first_message}]` |
| `GET /api/sessions/{id}` | Полная история сессии с отладочными данными | `{session, messages[], lead}` |
| `GET /api/leads` | Список заявок | `[{lead_id, session_id, created_at, full_name, phone, company}]` |
| `GET /api/leads/{id}` | Заявка с резюме | `{lead, summary}` |
| `GET /api/health` | Проверка живости | `{status, index_loaded}` |

Ошибки возвращаются как `{error: {code, message}}` с кодами 400, 404, 502 (сбой LLM), 504 (таймаут).

### Контракт 3. Резюме заявки (Иван → все)

| Поле | Содержание |
| --- | --- |
| `client_task` | Задача клиента своими словами, 1–2 предложения |
| `client_type` | Сегмент: бизнес, энергетик предприятия, СНТ, сетевая организация, менеджер МТС |
| `object_details` | Что известно об объекте: отрасль, число точек, что уже установлено |
| `recommended_products` | Продукты Energytool, которые бот назвал, с причиной |
| `open_questions` | Что клиент спрашивал и на что бот не ответил |
| `next_step` | О чём менеджеру стоит говорить в первую очередь |

В резюме попадают только факты из диалога. Чего клиент не говорил, пишется как «не уточнялось».

## ТЗ Ивана: RAG и логика консультанта

Иван отвечает за всё, что оценивает LLM-судья: какие фрагменты находятся и что бот на них отвечает. Результат работы: пакет `core/` с функцией `answer()` и рабочий `solution.py`.

### 1. База знаний и индекс

- Прочитать всю базу знаний и составить карту «задача клиента → продукт Energytool → сегмент». Карта нужна для промпта и для презентации.
- Написать скрипт `scripts/build_index.py`: читает исходные документы, режет на фрагменты по заголовкам и абзацам (ориентир 300–500 токенов, перекрытие 50), сохраняет у каждого `doc_id`, название документа, раздел, продукт.
- Посчитать эмбеддинги фрагментов моделью `BAAI/bge-m3` заранее и положить готовый индекс в репозиторий сабмита (файл матрицы плюс JSON с метаданными).
- Построить лексический индекс BM25 по тем же фрагментам. Он нужен для названий продуктов, моделей счётчиков и терминов, на которых эмбеддинги ошибаются.
- Исходные выгрузки базы знаний в открытый репозиторий не попадают (ограничение 1 кейса). Способ хранения согласовать с Арчи.

### 2. Поиск

- Гибридный поиск: top-20 по эмбеддингам и top-20 по BM25, объединение через Reciprocal Rank Fusion.
- Реранжирование `Qwen3 Reranker 8B` до top-5. Включается флагом `USE_RERANKER`; оставляем, только если прирост качества на тестовых вопросах оправдывает задержку.
- Для диалогов: один вызов LLM переписывает последнюю реплику в самостоятельный поисковый запрос с учётом истории. Для одиночного вопроса этот шаг пропускается.
- Порог уверенности по оценке лучшего фрагмента. Ниже порога бот не отвечает наугад, а выбирает `clarify` или `out_of_scope`.

### 3. Логика консультанта

- Системный промпт: роль консультанта Energytool, факты только из переданных фрагментов, простой язык без терминов, ответ до 150 слов, не больше одного уточняющего вопроса за реплику.
- Выбор действия из контракта 1: `answer`, `clarify`, `out_of_scope`, `offer_lead`, `collect_lead`, `lead_ready`.
- `clarify`: когда задача клиента допускает несколько продуктов и не хватает одного факта (тип объекта, есть ли счётчики, что именно болит).
- `out_of_scope`: ответа нет в базе, вопрос про настройку приборов или техдокументацию, либо тема не про Energytool. Бот прямо говорит, что не знает, и предлагает специалиста.
- `offer_lead`: бот уже назвал подходящий продукт, либо клиент спросил про цену, сроки, подключение, либо сам попросил связаться.
- Проверить, что всё работает именно на `Qwen3.8-27B`: формат вывода действия должен быть устойчивым (JSON с повтором при ошибке разбора или отдельный короткий вызов-классификатор).

### 4. Сбор заявки

- В режиме `collect_lead` бот спрашивает недостающее из трёх полей: ФИО, телефон, название компании. Уже названное в диалоге повторно не спрашивает.
- Извлечение полей из реплик: телефон регулярным выражением с нормализацией к `+7XXXXXXXXXX`, ФИО и компания через LLM.
- Когда все три поля есть, сформировать резюме по контракту 3 и вернуть `lead_ready`. Лимит 150 слов на резюме не действует.
- Пользователь может уйти от заявки на другой вопрос и вернуться: собранные поля восстанавливаются из истории, а не из памяти процесса.

### 5. solution.py и замеры

- `solution.py` по формату Технического регламента: читает тест-кейсы, вызывает `core.answer()`, пишет выходной файл по образцу организаторов. Никаких обращений к серверу, БД и сети, кроме API организаторов.
- Скрипт `scripts/eval.py`: прогоняет тестовые вопросы из материалов кейса, сохраняет ответы, найденные документы и время. Каждое изменение промпта или поиска проверяется этим прогоном до сабмита.
- Журнал сабмитов в `docs/submits.md`: дата, что изменили, балл лидерборда.
- В поле `debug.timings_ms` отдавать время каждого шага. Ориентир: полный ответ до 5 секунд на платформенной модели.

### Критерии приёмки

- [ ] `core.answer()` возвращает результат строго по контракту 1 на всех тестовых вопросах
- [ ] На вопрос вне базы знаний бот не выдумывает ответ и предлагает специалиста
- [ ] На размытый запрос бот задаёт один уточняющий вопрос
- [ ] Диалоговый тест: ответ учитывает историю, а не только последнюю реплику
- [ ] Полный сценарий от вопроса до `lead_ready` проходит без сервера, только через `answer()`
- [ ] Первый сабмит на платформу отправлен и получил балл выше 0
- [ ] Ответы на типовые вопросы укладываются в 150 слов

## ТЗ Арчи: API-сервер, хранение и деплой

Арчи отвечает за допуск к экспертной оценке: решение должно запускаться одной командой и проходить сценарий от первого вопроса до заявки. Критерий «Работоспособность» весит 30% экспертной оценки, «Безопасность, зависимости и документация» ещё 10%.

### 1. API-сервер

- FastAPI-приложение в `server/`, реализует все эндпоинты контракта 2.
- На этапе 1 ядро заменено заглушкой с тем же интерфейсом (`core.answer()` возвращает фиксированный ответ), чтобы не ждать Ивана.
- На каждый `POST /messages`: загрузить историю сессии из БД, вызвать ядро, сохранить реплику пользователя и ответ бота с полями `action`, `sources`, `debug`.
- Контекст живёт только внутри сессии. Новая сессия получает новый `session_id` и пустую историю; данные других сессий в ядро не передаются.
- Вызов ядра вынесен из event loop (пул потоков), чтобы параллельные диалоги не блокировали друг друга.
- Таймаут на ответ ядра 30 секунд, один повтор при сетевой ошибке LLM. При сбое пользователь получает понятное сообщение, а не трассировку.

### 2. Хранение

SQLite-файл в Docker-томе, три таблицы:

| Таблица | Поля |
| --- | --- |
| `sessions` | `id`, `started_at`, `last_message_at` |
| `messages` | `id`, `session_id`, `role`, `content`, `action`, `sources_json`, `debug_json`, `created_at` |
| `leads` | `id`, `session_id`, `full_name`, `phone`, `company`, `summary_json`, `created_at` |

- Сохраняются все сессии, включая те, что не дошли до заявки (требование 5 постановки и ограничение 6).
- Заявка создаётся, когда ядро вернуло `lead_ready`. Повторный `lead_ready` в той же сессии обновляет запись, а не создаёт вторую.
- Телефон проверяется на сервере: 11 цифр, формат `+7XXXXXXXXXX`.

### 3. Конфигурация и секреты

- Все внешние подключения через переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `EMBED_BASE_URL`, `EMBED_MODEL`, `RERANK_BASE_URL`, `USE_RERANKER`, `DB_PATH`.
- `.env.example` с пустыми значениями и комментариями. Рабочий `.env` в `.gitignore` и `.dockerignore`.
- Проверка перед каждым пушем: в репозитории нет ключей и нет исходных выгрузок базы знаний.

### 4. Docker и деплой

- `Dockerfile`, `compose.yaml`, `.dockerignore`. Запуск всего решения одной командой: `docker compose up --build`.
- Фронтенд собирается на этапе сборки образа и раздаётся тем же контейнером как статика. Один сервис, один порт.
- Зависимости с зафиксированными версиями: `requirements.txt` для Python, `package-lock.json` для фронтенда.
- Публичный стенд на VPS с HTTPS. Ссылка идёт на первый слайд презентации.
- Проверка с чистой машины: клонировать репозиторий, заполнить `.env`, выполнить одну команду, пройти сценарий.

### 5. Сборка сабмита и документация

- Скрипт `scripts/make_submit.sh`: собирает ZIP с `solution.py`, пакетом `core/`, готовым индексом и `requirements.txt` по Техническому регламенту.
- Локальная проверка архива в Docker-образе, близком к платформенному, до загрузки.
- `README.md`: назначение и архитектура, команда запуска, переменные окружения, порты, зависимости, порядок проверки основного сценария, известные ограничения, какой внешний API и какая модель используются.

### 6. Сценарий внедрения

- Одностраничное описание в `docs/integration.md`: как чат встраивается в сайт Energytool и как заявка попадает менеджеру.
- Встраивание: тег `<script>`, который добавляет плавающую кнопку и открывает чат во фрейме (реализует Андрей).
- Передача заявки: исходящий вебхук с JSON заявки и резюме. В прототипе это заглушка, которая пишет в лог; реальная интеграция с CRM не требуется.

### Критерии приёмки

- [ ] `docker compose up --build` на чистой машине поднимает чат без ручных шагов
- [ ] Все эндпоинты контракта 2 работают и возвращают описанные поля
- [ ] После перезапуска контейнера история сессий и заявки сохраняются
- [ ] Две сессии в разных вкладках не видят контекст друг друга
- [ ] При недоступном LLM чат показывает сообщение об ошибке и остаётся рабочим
- [ ] В репозитории нет секретов и исходных выгрузок базы знаний
- [ ] Архив сабмита проходит локальную проверку в Docker
- [ ] README позволяет запустить решение человеку, который не видел проект

## ТЗ Андрея: веб-интерфейс чата

Андрей отвечает за то, что эксперты увидят глазами: без рабочего чата команда не допускается к оценке вообще. Результат работы: приложение в `web/` на React, Vite и TypeScript, которое проходит сценарий от первого вопроса до заявки.

### 1. Чат

- Лента сообщений пользователя и бота, поле ввода, отправка по Enter, перенос строки по Shift+Enter.
- Индикатор «бот печатает», пока ждём ответ. Поле ввода на это время заблокировано.
- Ответ бота рендерится как Markdown (списки, выделение), ссылки открываются в новой вкладке.
- На пустом экране 4–5 кнопок-подсказок с типовыми задачами аудитории: выросли счета, нужен учёт по СНТ, ищем потери, подозреваем хищения. Нажатие отправляет текст как первую реплику.
- Кнопка «Новый диалог»: создаёт новую сессию через `POST /api/sessions` и очищает ленту.
- `session_id` хранится в `sessionStorage`. Закрытие вкладки начинает диалог с чистого листа (ограничение 6 кейса).
- Ошибка сети или сервера: сообщение в ленте и кнопка «Повторить», введённый текст не теряется.
- Вёрстка работает на ширине от 360 px.

### 2. Реакция на действия бота

Интерфейс читает поле `action` из контракта 1:

- `out_of_scope` и `offer_lead`: под ответом кнопка «Связаться с менеджером». Нажатие отправляет реплику «Хочу связаться с менеджером».
- `collect_lead`: над полем ввода строка прогресса из трёх пунктов (ФИО, телефон, компания) с отметкой уже собранных.
- `lead_ready`: карточка «Заявка передана менеджеру» с тремя полями и раскрывающимся резюме по контракту 3.
- Сбор контактов идёт репликами в чате, а не отдельной формой: так сценарий одинаков в демо и в автопроверке.

### 3. Режим отладки

- Переключатель «Отладка» в шапке, состояние запоминается в `localStorage`.
- Под каждым ответом бота во включённом режиме: общее время ответа, разбивка по шагам (`rewrite`, `retrieval`, `rerank`, `llm`), значение `action`, поисковый запрос.
- Список использованных документов базы знаний: название, оценка релевантности, фрагмент. Фрагмент раскрывается по клику.
- Время ответа дополнительно замеряется на клиенте (от отправки до получения), чтобы была видна сетевая задержка.

### 4. История сессий и заявки

- Страница «История»: таблица всех сессий с датой, первой репликой, числом сообщений и отметкой о заявке. Сессии без заявки тоже показываются.
- Клик по сессии открывает переписку только для чтения, с теми же отладочными данными.
- Страница «Заявки»: список заявок, клик открывает резюме и ссылку на исходную сессию.

### 5. Режим виджета

- Параметр `?embed=1` показывает чат без шапки и навигации, для вставки во фрейм.
- Демо-страница `demo.html`: условная страница сайта с плавающей кнопкой в правом нижнем углу, которая открывает чат в панели. Это наглядное доказательство сценария внедрения для защиты.

### 6. Порядок работы и стиль

- До готовности сервера работать на моках: файл `web/src/api/mock.ts` отдаёт ответы по контрактам 1 и 2 для всех шести значений `action`.
- Переключение мок ↔ настоящий API через переменную `VITE_API_URL`.
- Визуальный стиль: светлая тема, акцентный красный в духе МТС, без копирования фирменных элементов и логотипа.
- В примерах и скриншотах только выдуманные ФИО, телефоны и компании (ограничение 8 кейса).
- Сделать 6–8 скриншотов основного сценария и режима отладки для презентации.

### Критерии приёмки

- [ ] Сценарий «вопрос → уточнение → рекомендация → контакты → карточка заявки» проходится без перезагрузки страницы
- [ ] «Новый диалог» очищает ленту, и бот не помнит прошлую переписку
- [ ] В режиме отладки у каждого ответа видны время и использованные документы

- [ ] Интерфейс читается на телефоне шириной 360 px

## Порядок работ

Главное правило: сквозной работающий сценарий и первый сабмит появляются как можно раньше, качество наращивается поверх них. Лидерборд даёт половину онлайн-оценки, и каждый ранний сабмит — это обратная связь, которую иначе не получить.

| Этап | Иван | Арчи | Андрей | Результат этапа |
| --- | --- | --- | --- | --- |
| 1. Каркас | Читает базу знаний и Технический регламент, пишет заглушку `core.answer()` | Поднимает FastAPI с заглушкой ядра, SQLite, compose | Собирает чат на моках | Контракты зафиксированы, у каждого запускается своя часть |
| 2. Сквозной сценарий | Простой RAG: эмбеддинги, top-5, один промпт; первый сабмит | Подключает настоящее ядро, выкатывает стенд | Переключается на настоящий API | Чат отвечает по базе знаний, есть балл на лидерборде |
| 3. Качество | Гибридный поиск, реранкер, действия, сбор заявки; сабмиты после каждого улучшения | История, заявки, обработка ошибок, сборка сабмита | Отладка, история, карточка заявки | Полный сценарий до заявки работает на стенде |
| 4. Сдача | Слайды про архитектуру и поиск, ограничения | README, проверка с чистой машины, `docs/integration.md` | Режим виджета, скриншоты, оформление презентации | Материалы финальной сдачи загружены |

Точки синхронизации:

- **Конец этапа 1.** Общий созвон на 20 минут: проходим три контракта, после него они заморожены.
- **Конец этапа 2.** Втроём проходим сценарий на стенде и записываем, что сломано.
- **За сутки до дедлайна.** Заморозка кода: дальше только исправления ошибок, README и презентация.
- **Ежедневно.** Короткое сообщение в чат команды: что сделал, что блокирует.

Этап 4 не сжимать: полный комплект материалов является условием допуска, а не бонусом.

## Общие правила

Эти требования взяты из кейса и касаются всех троих; нарушение любого из них бьёт по допуску или по критерию «Безопасность, зависимости и документация».

- **Данные кейса.** Исходные выгрузки базы знаний не публикуются в открытых репозиториях и не передаются третьим лицам. Репозиторий держим приватным с доступом для аккаунта жюри `hack-and-change-2026`.
- **Секреты.** Ключи API не попадают ни в код, ни в историю коммитов, ни в презентацию.
- **Персональные данные.** В тестах, демо и скриншотах только выдуманные ФИО, телефоны и компании.
- **Факты.** Бот берёт сведения о продуктах, ценах и условиях только из базы знаний. Знания модели об энергетике использовать нельзя.
- **Одна ветка правды.** Работаем через pull request в `main`; `main` всегда запускается одной командой.
- **Структура репозитория.** `core/`, `server/`, `web/`, `scripts/`, `docs/`, в корне `solution.py`, `Dockerfile`, `compose.yaml`, `README.md`, `.env.example`.
