# Критерии приёмки серверной части и инфраструктуры (зона Arthur)

Каждый критерий бинарный: прошёл или не прошёл. В скобках в конце — требования из `requirements.md`, которые он закрывает. Условности в командах: `$H` — адрес сервера (локально `http://localhost:8000`), `$S` — адрес стенда, `$T` — код доступа стенда; имена скриптов в `server/scripts/` условные и фиксируются при реализации. Проверки с пометкой «заглушка» выполняются на заглушке ядра (SRV-12), без сети и ключей. Все тестовые ФИО, телефоны и компании — вымышленные.

## Условия допуска к экспертной оценке

Невыполнение любого пункта означает, что команда не допускается (кейс, стр. 11). Проверяются последними, на финальном коммите.

- [ ] **AC-SRV-01. Запуск одной командой.** На машине без кеша Docker (`docker system prune -a` или новая виртуальная машина): клон репозитория → шаги из README (ключ в `.env`, база знаний по принятому способу) → `docker compose up --build` завершает сборку без ошибок, и не позже чем через 3 минуты после старта контейнера `curl -fsS $H/api/health` возвращает 200 и `"index_loaded": true`. Других команд не выполнялось. (SRV-13, SRV-16, SRV-21, SRV-38)
- [ ] **AC-SRV-02. Основной сценарий до заявки.** В браузере на локальном запуске из AC-SRV-01: первый вопрос → ответ по базе знаний → согласие связаться с менеджером → ввод ФИО, телефона, компании репликами → карточка заявки. После этого `GET $H/api/leads` содержит ровно одну новую запись с тремя полями и резюме, а сессия видна на странице истории. То же пройдено на стенде `$S`. (SRV-10, SRV-28, SRV-29, SRV-25)
- [ ] **AC-SRV-03. Полный комплект материалов.** `ls README.md Dockerfile compose.yaml .dockerignore .env.example` не выдаёт ошибок; есть файл зависимостей сервера, где каждая строка содержит точную версию, и lock-файл фронтенда; презентация PDF приложена, на первом слайде — порядок проверки и ссылка на репозиторий. (SRV-39)
- [ ] **AC-SRV-04. Сабмит с ненулевым баллом.** В `docs/submits.md` есть запись об отправке с баллом платформы больше 0 и идентификатором коммита. (SRV-24)
- [ ] **AC-SRV-05. Доступ жюри.** Репозиторий открывается из браузера без авторизации либо, если он приватный, в списке участников есть `hack-and-change-2026`; проверено из чужой учётной записи или окна инкогнито. (SRV-39)

## Этап 1. Каркас

- [ ] **AC-SRV-06. Игнор-файлы.** `git check-ignore -q .env data/knowledge-base.zip dist/x.zip` возвращает 0 для каждого пути; `.env.example` не игнорируется. В контексте сборки нет `.env`, `.git`, `data/`: проверка содержимого образа из AC-SRV-33. (SRV-02)
- [ ] **AC-SRV-07. Проверка на утечки ловит нарушения.** На чистом дереве скрипт проверки возвращает 0. После добавления в индекс git временного файла со строкой вида `LLM_API_KEY=<40 случайных символов>` — возвращает не 0; после добавления копии любого файла базы знаний под другим именем — возвращает не 0. В тексте самого скрипта нет строк из материалов кейса (просмотр на ревью). (SRV-03)
- [ ] **AC-SRV-08. `.env.example`.** Каждая переменная из таблицы SRV-04 присутствует в файле; `grep -E '(KEY|TOKEN)=.+' .env.example` ничего не находит. (SRV-06)
- [ ] **AC-SRV-09. Имена переменных платформы.** Три запуска с одним и тем же вопросом дают ответ 200: заданы только `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; заданы только `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `GEN_MODEL`; основная переменная равна собственному имени, а запасная задана верно. `grep -rniE 'qwen|bge-m3' --include='*.py' server/` ничего не находит: имена моделей приходят только из окружения. (SRV-04, SRV-05)
- [ ] **AC-SRV-10. Старт без `.env` и без базы.** На клоне без `.env` и без `data/`: `docker compose up --build -d` завершается с кодом 0, `curl -fsS $H/api/health` возвращает 200 с `"index_loaded": false`, главная страница открывается. (SRV-13)
- [ ] **AC-SRV-11. Эндпоинты контракта 2 (заглушка).** Сценарий из `curl`-запросов: `POST /api/sessions` → есть `session_id`; `POST /api/sessions/{id}/messages` с `{"text":"..."}` → 200 и поля `answer`, `action`, `sources`, `lead`, `debug`, `message_id`; `GET /api/sessions` содержит эту сессию с `messages_count: 2`; `GET /api/sessions/{id}` возвращает две реплики в порядке отправки; `GET /api/leads` → 200; `GET /api/nope` → 404 с JSON-телом ошибки. В `server/` нет промптов и текстов о продуктах: Иван подтверждает на ревью. (SRV-07, SRV-01)
- [ ] **AC-SRV-12. Модель ошибок.** Пустой `text` → 400 `invalid_request`; несуществующая сессия → 404 `session_not_found`; текст длиннее лимита → 413 `message_too_long`. Каждое тело содержит `error.code`, `error.message`, `error.retryable`, `error.request_id`; ни в одном нет подстрок `Traceback`, `File "`, адреса API. (SRV-08)
- [ ] **AC-SRV-13. Идентификаторы сессий.** 1000 вызовов `POST /api/sessions` дают 1000 разных значений; формат — не короче 22 символов URL-безопасного алфавита или UUID версии 4. (SRV-09)
- [ ] **AC-SRV-14. Сохранность после пересоздания контейнера.** Создать сессию с репликой → `docker compose down && docker compose up -d` → `GET /api/sessions/{id}` возвращает те же реплики. (SRV-11, SRV-13)
- [ ] **AC-SRV-15. Сборщик, первая версия.** Скрипт сборки создаёт архив в `dist/`; `unzip -l` показывает `solution.py` и `requirements.txt` без префикса папки; `git status --short dist/` пуст (каталог игнорируется). (SRV-14)

## Этап 2. Сквозной сценарий и стенд

- [ ] **AC-SRV-16. Изоляция сессий и сброс контекста (заглушка).** В сессии A отправлены три реплики, затем создана сессия B и отправлена одна: заглушка сообщает, что получила ровно одну реплику, и её текст совпадает с отправленным в B. Повторная реплика в A получает историю только A. (SRV-09, SRV-10)
- [ ] **AC-SRV-17. Идемпотентность реплики (заглушка).** Два одинаковых `POST .../messages` с одним `client_message_id` подряд: одинаковый `message_id` в ответах, `messages_count` сессии равен 2, счётчик вызовов заглушки равен 1. (SRV-10)
- [ ] **AC-SRV-18. Параллельные диалоги (заглушка с задержкой 3 с).** 10 сессий отправляют по реплике одновременно: все ответы 200, общее время не больше 6 с, каждый ответ содержит метку своей сессии. (SRV-17)
- [ ] **AC-SRV-19. Одна сессия — одна реплика за раз (заглушка с задержкой 3 с).** Два одновременных запроса в одну сессию с разными `client_message_id`: один получает 200, другой 409 `session_busy`. При пределе одновременных вызовов 2 и трёх одновременных сессиях третья получает 503 `overloaded` не позже чем через 1 с. (SRV-17)
- [ ] **AC-SRV-20. Таймаут (заглушка с задержкой 60 с, `CORE_TIMEOUT_S=30`).** Ответ 504 `llm_timeout` приходит через 30 ± 2 с; следующая реплика в той же сессии при задержке 0 получает 200. (SRV-18, SRV-19)
- [ ] **AC-SRV-21. Повторы только в одном слое.** С настоящим ядром и заглушкой API моделей, которая всегда отвечает 500: на один шаг обработки приходит не больше двух запросов (по журналу заглушки), клиент получает 502 `llm_error`. Если 500 возвращается один раз, а затем 200 — клиент получает 200. (SRV-18) Зависит от: CORE.
- [ ] **AC-SRV-22. Недоступная модель.** При `LLM_BASE_URL=http://127.0.0.1:9`: отправка реплики возвращает 502 или 504 не позже чем через `CORE_TIMEOUT_S` + 2 с; `GET /api/sessions/{id}` показывает реплику пользователя с отметкой ошибки; `GET /api/sessions` и `GET /api/leads` возвращают 200; после возврата верного адреса следующая реплика в той же сессии получает 200. (SRV-19, SRV-10)
- [ ] **AC-SRV-23. База знаний и индекс.** С базой в `data/`: `index_loaded` становится `true`, ответ на вопрос из демо-набора содержит непустой `sources`. Без файла базы: отправка реплики возвращает 503 `not_ready`, а `error.message` называет путь, куда положить файл. Второй старт контейнера с той же базой достигает `index_loaded: true` быстрее первого и без обращений к API эмбеддингов (по журналу). (SRV-16)
- [ ] **AC-SRV-24. Один код ядра.** Контрольные суммы файлов ядра в образе (`docker compose exec`) и в распакованном ZIP совпадают; `version` в `/api/health` равен идентификатору коммита в манифесте архива. (SRV-15)
- [ ] **AC-SRV-25. Структура ZIP.** Проверка архива проходит: размер не больше 128 МБ; в корне есть `solution.py` и `requirements.txt`; `unzip -Z1 dist/*.zip | grep -E '/.*\.py$'` пуст; в списке нет `questions.csv`, `knowledge-base.zip`, `.env`, файлов сервера и фронтенда; каждая строка `requirements.txt` дословно присутствует в разрешённом наборе организаторов; `grep -rnE 'pip +install'` по распакованному архиву ничего не находит. Сборка из незакоммиченного дерева завершается ошибкой. (SRV-22)
- [ ] **AC-SRV-26. Прогон как на платформе.** Скрипт локальной проверки запускает архив в чистом контейнере с `--cpus 8 --memory 16g`, только с переменными платформы, и завершается с кодом 0: `solution.py` отработал быстрее 20 минут; `submission.csv` в рабочем каталоге, заголовок ровно `id,answer`, множество ID равно входному, повторов нет, пустых ответов нет, длина каждого не больше 10 000 символов. Входной набор включает диалоговые вопросы с переводами строк. В отчёте есть время на вопрос и оценка числа вопросов, помещающихся в 20 минут. (SRV-23)
- [ ] **AC-SRV-27. Сабмит при сбоях модели.** Тот же прогон с недоступным API моделей: `solution.py` завершается с кодом 0, а `submission.csv` проходит все проверки формата из AC-SRV-26. (SRV-23) Зависит от: CORE.
- [ ] **AC-SRV-28. Стенд по HTTPS.** `curl -fsS $S/api/health` (без `-k`) возвращает 200; `curl -sI http://<домен стенда>/` возвращает 301 или 308 на `https://`; страницы истории и `?embed=1` открываются по прямой ссылке; страница `demo.html` показывает чат во фрейме. (SRV-25, SRV-21)
- [ ] **AC-SRV-29. Защита стенда.** Без кода доступа `GET $S/api/sessions`, `GET $S/api/leads`, `GET $S/api/leads/{id}` возвращают 401; с кодом `$T` — 200. `POST $S/api/sessions` и отправка реплики работают без кода, и в их ответах нет фрагментов документов. Локально при пустом `ADMIN_TOKEN` все эти запросы возвращают 200 без кода. (SRV-26) Зависит от: Q-SRV-13.
- [ ] **AC-SRV-30. Лимиты стенда.** Запросы сверх `RATE_LIMIT_PER_MIN` с одного адреса получают 429 с заголовком `Retry-After`; реплика сверх `MAX_SESSION_MESSAGES` получает ошибку в формате SRV-08; после паузы из `Retry-After` запрос проходит. (SRV-27)
- [ ] **AC-SRV-31. Комбинация моделей для стенда.** В README указана проверенная комбинация «сервис — модель генерации — модель эмбеддингов — реранкер или его отключение», и на стенде `debug` ответа показывает, что шаги поиска и генерации выполнены без ошибок. (SRV-20)

## Этап 3. Качество

- [ ] **AC-SRV-32. История для проверки.** После трёх диалогов (без заявки, с заявкой, с ошибкой модели) `GET /api/sessions` возвращает все три, от новых к старым, с верными `has_lead` и `messages_count`; параметр размера страницы ограничивает выдачу; в `GET /api/sessions/{id}` у каждого ответа бота есть `action`, `sources` и `debug.timings_ms`. Те же три сессии видны на странице истории интерфейса. (SRV-28, SRV-11)
- [ ] **AC-SRV-33. Образ и зависимости.** `docker compose exec <сервис> id -u` возвращает не 0; поиск в файловой системе образа не находит `.env`, `.git`, `knowledge-base.zip` (кроме подключённого каталога данных); `docker history --no-trunc <образ>` не содержит значения ключа; в файлах зависимостей сервера нет строк без точной версии; сборка фронтенда использует установку строго по lock-файлу. (SRV-33, SRV-21)
- [ ] **AC-SRV-34. Заявка и идемпотентность.** Сценарий до `lead_ready` (заглушка): в `GET /api/leads` одна запись с `full_name`, `phone`, `company`, а `GET /api/leads/{id}` отдаёт резюме с шестью полями контракта 3 и `session_id`. Повторный `lead_ready` в той же сессии, в том числе два одновременных: запись по-прежнему одна, `updated_at` изменился. (SRV-29)
- [ ] **AC-SRV-35. Телефон.** Таблица проверок общей функции: согласованные в Q-SRV-16 варианты записи одного номера приводятся к `+7` и 10 цифрам; строки короче или длиннее, с буквами и с другим кодом страны отклоняются. `lead_ready` с отклонённым номером не создаёт запись в `GET /api/leads`, а пользователь получает ответ без ошибки сервера. (SRV-30)
- [ ] **AC-SRV-36. Передача менеджеру.** После создания заявки `GET /api/leads/{id}` содержит состояние передачи со статусом и временем; событий передачи на создание — ровно одно. При недоступном `LEAD_WEBHOOK_URL` пользователь всё равно получает 200, статус передачи отражает неудачу. (SRV-31)
- [ ] **AC-SRV-37. Журнал без секретов и персональных данных.** После сценария с заявкой `docker compose logs` не содержит значения `LLM_API_KEY`, подстроки `Bearer `, введённого телефона и ФИО (четыре `grep -c` дают 0); каждая строка об обработке реплики содержит `request_id` и время. (SRV-32, SRV-05)
- [ ] **AC-SRV-38. Автотесты.** Одна команда из README запускает тесты сервера без сети и без `.env`; код возврата 0; в отчёте есть тесты на каждый код из таблицы SRV-08. (SRV-34, SRV-12)
- [ ] **AC-SRV-39. Накладные расходы сервера (заглушка без задержки).** 100 последовательных реплик: 95-й процентиль времени ответа не больше 100 мс. (SRV-17, SRV-10)
- [ ] **AC-SRV-40. Стенд переживает перезагрузку.** После перезагрузки хоста `$S/api/health` возвращает 200 не позже чем через 3 минуты без ручных действий, ранее созданные сессии на месте. Остановка контейнера вручную вызывает уведомление команде не позже чем через 5 минут. Учебное восстановление по инструкции из `deploy/` на новом хосте с резервной копией занимает не больше 30 минут. (SRV-35)
