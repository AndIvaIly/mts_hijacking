## Этап 1. Каркас

**SRV-01. Границы области и правила.** Все файлы Arthur лежат в `server/`, `deploy/` и корневых `Dockerfile`, `compose.yaml`, `.dockerignore`, `.env.example`; чужие области не меняются, общая зона — через pull request. Сервер не содержит логики консультанта (поиск, промпты, выбор действия, тексты о продуктах) — только вызывает ядро. Выбор стека, хранилища и каждое изменение контракта записаны строкой в decision log до кода; цели `lint` и `test` в `server/Makefile` выполняют настоящие проверки. (правила, D-2, D-3; кейс, стр. 10, п. 2) Зависит от: Q-SRV-11.

**SRV-02. Игнор-файлы раньше кода.** Общий `.gitignore` уже закрывает `data/`, `.env*`, архивы, базы данных и `dist/` (D-5). До первого кода Arthur создаёт `.dockerignore` с тем же составом плюс `.git`, а недостающие шаблоны (файлы индекса, журналы, резервные копии хранилища) добавляет в `.gitignore` через pull request. В репозиторий не попадают: база знаний и её дословные фрагменты, тестовые вопросы, пример выходного файла, собранный ZIP-сабмит, индекс с текстами фрагментов. Образы с базой знаний внутри не публикуются в открытых реестрах. (кейс, стр. 10, п. 1 и 9; стр. 13; правила)

**SRV-03. Проверка на утечки сверх общей.** Общая проверка `make lint` (`scripts/checks.py`) ловит запрещённые имена файлов и строки, похожие на ключи. Она не видит: текст базы знаний и вопросов, вставленный в код, тесты, моки и документы; историю коммитов; содержимое собранного ZIP и образа. Arthur закрывает эти пробелы проверкой, которая завершается ненулевым кодом при находке, не содержит текста материалов кейса (сверка по хешам или эквивалентно), запускается перед пушем и внутри сборки сабмита и умеет проверять всю историю. Место проверки — `server/scripts/` либо доработка общей через pull request. (кейс, стр. 10, п. 1 и 9; правила; способ — Q-SRV-04)

**SRV-04. Единые имена переменных окружения.** Одни и те же имена действуют на платформе, на стенде и локально. Имена платформы не переименовываются; свои переменные добавляются только как необязательные, с запасным значением, чтобы на платформе решение работало без них.

**SRV-05. Правила чтения конфигурации.** Настройки моделей читает один модуль ядра, сервер их не дублирует. Пустое значение и значение, равное имени самой переменной, считаются незаданными; запасные имена перебираются в порядке из таблицы; числовые параметры ограничиваются допустимым диапазоном (пример сабмита). Идентификатор модели и адрес API в коде не фиксируются (регламент, §6). Значения ключей не попадают в код, файлы и журналы (регламент, §6; кейс, стр. 10, п. 9). Зависит от: CORE.

**SRV-06. `.env.example`.** Содержит все переменные из SRV-04 с комментарием на русском; значения ключей и кодов доступа пустые; несекретные значения по умолчанию заполнены так, что после добавления одного ключа решение запускается. (кейс, стр. 8; ТЗ)

**SRV-07. Эндпоинты.** Реализованы пути контракта 2; все ответы — JSON в UTF-8, время — UTC в ISO 8601. (ТЗ; уточнения — предложение, Q-SRV-15)

| Метод и путь | Поведение | Доступ |
| --- | --- | --- |
| `POST /api/sessions` | Создаёт диалог, возвращает `{session_id, started_at}` | клиент |
| `POST /api/sessions/{id}/messages` | Тело `{text, client_message_id?}`; возвращает результат ядра по контракту 1 плюс `message_id`, `session_id`, `created_at` и `lead_id` при `lead_ready`. `sources` — всегда массив, `lead` и `debug` — объект или `null` | клиент |
| `GET /api/sessions/{id}` | `{session, messages[], lead}`; реплики в хронологическом порядке; у ответов бота — `action`, `sources`, `debug` и снимок `lead` на момент ответа | клиент по своему идентификатору; отладочные поля — по Q-SRV-13 |
| `GET /api/sessions` | Список сессий, включая сессии без заявки, от новых к старым; `lead_id` у сессий с заявкой; постраничный | проверка |
| `GET /api/leads`, `GET /api/leads/{id}` | Список заявок; заявка с резюме и статусом передачи | проверка |
| `GET /api/health` | `{status, index_loaded, version}`; отвечает всегда, пока процесс жив | открыт |

Неизвестный путь под `/api/` возвращает JSON-ошибку 404, а не страницу фронтенда. Состав полей сверен с ожиданиями интерфейса (раздел «Жду от Arthur» в `web/docs/requirements.md`).

**SRV-08. Модель ошибок.** Любая ошибка — `{"error": {"code", "message", "retryable", "request_id"}}`. `message` — текст на русском, пригодный для показа пользователю; без трассировок, внутренних путей, адресов API и без сведений о продуктах. (ТЗ; расширение — предложение)

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `invalid_request` | Некорректный JSON, пустой `text`, неверные типы |
| 401 | `unauthorized` | Нет или неверен код доступа к защищённому пути |
| 404 | `session_not_found`, `lead_not_found`, `not_found` | Объекта или пути нет |
| 409 | `session_busy` | В этой сессии уже обрабатывается реплика |
| 413 | `message_too_long` | `text` длиннее `MAX_MESSAGE_CHARS` |
| 429 | `rate_limited` | Превышен лимит; заголовок `Retry-After` |
| 502 | `llm_error` | Модель вернула ошибку или непригодный ответ после повторов |
| 503 | `not_ready`, `overloaded` | Индекс не загружен или нет базы знаний; исчерпан предел одновременных вызовов |
| 504 | `llm_timeout` | Истёк `CORE_TIMEOUT_S` |
| 500 | `internal` | Всё остальное; подробности только в журнале по `request_id` |

**SRV-09. Сессии, изоляция и сброс контекста.** Каждая сессия получает новый непредсказуемый идентификатор (не менее 122 случайных бит) и пустую историю. В ядро передаются реплики только этой сессии; сервер не связывает сессии между собой ни по адресу, ни по cookie, ни по браузеру и не держит контекст диалога в памяти процесса — только в хранилище. «Новый диалог» на стороне сервера — это создание новой сессии; прежняя остаётся в истории без изменений. (кейс, стр. 6, п. 5; стр. 10, п. 6; ТЗ)

**SRV-10. Обработка реплики и повтор.** Порядок: проверка запроса → вызов ядра с историей сессии и новой репликой → при успехе реплика пользователя и ответ бота сохраняются одной неделимой операцией вместе с `action`, `sources`, `debug`, снимком `lead` и временем обработки → ответ клиенту. При сбое ядра в историю не пишется ничего, поэтому в ней нет реплик без ответа, а повтор безопасен; сбой фиксируется в журнале по `request_id`. Повтор запроса с тем же `client_message_id` после успешного сохранения возвращает сохранённый ответ, не создаёт вторую пару реплик и не вызывает ядро. Отладочные данные запрашиваются у ядра и сохраняются всегда, независимо от режима интерфейса; `sources` и `debug` хранятся без изменений. (кейс, стр. 6, п. 5; ТЗ; CORE; правило повтора — предложение, Q-SRV-15, Q-WEB-10) Зависит от: WEB.

**SRV-11. Хранение.** Сохраняются все сессии с репликами, включая не дошедшие до заявки. Сущности: сессия (`id`, `started_at`, `last_message_at`), реплика (`id`, `session_id`, `role`, `content`, `action`, `sources`, `debug`, снимок `lead`, `client_message_id`, `latency_ms`, `created_at`), заявка (`id`, `session_id` — уникален, `full_name`, `phone`, `company`, `summary`, `created_at`, `updated_at`, состояние передачи). Данные лежат в именованном томе и переживают пересоздание контейнера; одновременная запись из параллельных диалогов не приводит к ошибкам блокировки. (кейс, стр. 6, п. 5; стр. 10, п. 6; ТЗ; выбор хранилища — Q-SRV-11)

**SRV-12. Заглушка ядра.** До готовности ядра сервер работает с заглушкой той же сигнатуры, которую даёт Иван (CORE-14). Для тестов сервера у Arthur есть собственный тестовый двойник с той же сигнатурой, который умеет: вернуть любое из шести значений `action`; сообщить, сколько реплик получил (проверка изоляции); выдержать заданную задержку; выбросить каждую из ошибок ядра. Двойник остаётся в тестах после подключения настоящего ядра. (ТЗ; режимы — предложение)

**SRV-13. Каркас Docker.** В корне есть `Dockerfile`, `compose.yaml` (именно это имя) и `.dockerignore`; `docker compose up --build` поднимает все компоненты, один сервис, один порт (на хосте — `APP_PORT`). Отсутствие файла `.env` не ломает запуск: без ключа и без базы знаний сервис стартует, `/api/health` отвечает 200, чат показывает понятное сообщение о том, чего не хватает. В `compose.yaml` заданы именованный том для хранилища, подключение файла базы знаний из `./data` только для чтения (остальные материалы кейса в контейнер не попадают), проверка здоровья и автоперезапуск. (кейс, стр. 8; ТЗ; деградированный режим — предложение)

**SRV-14. Сборщик сабмита, первая версия.** Скрипт в `server/scripts/` собирает ZIP из закоммиченного состояния: `solution.py` и `requirements.txt` в корне, без внешней папки. Готов до первого рабочего `solution.py`, чтобы первый сабмит не ждал этапа 3. (регламент, §4; расхождение 15) Зависит от: Q-SRV-08, CORE.

## Этап 2. Сквозной сценарий и стенд

**SRV-15. Один код ядра.** Сервер и ZIP-сабмит используют одни и те же файлы ядра без копий и правок; `/api/health` и манифест в ZIP показывают один и тот же идентификатор коммита. Ядро инициализируется один раз при старте; до готовности `index_loaded=false`. (ТЗ; регламент, §4) Зависит от: CORE, Q-SRV-08, Q-SRV-14.

**SRV-16. База знаний и индекс при запуске.** Источник базы знаний на стенде и у жюри — тот же, что на платформе: файл `knowledge-base.zip` в каталоге `DATA_DIR` (пример сабмита). Способ, которым файл попадает к жюри, определяет Q-SRV-07; в README он описан как явный шаг. Если базы нет или индекс ещё строится: сервис работает, `index_loaded=false`, отправка реплики возвращает 503 `not_ready` с указанием, куда положить файл. Построенный индекс кешируется в томе и перестраивается при смене базы или модели эмбеддингов. Модель эмбеддингов запроса совпадает с моделью, которой построен индекс. (кейс, стр. 9, п. 1; стр. 10, п. 1; кеш — предложение) Зависит от: CORE, Q-SRV-07, Q-SRV-09, Q-SRV-23, Q-SRV-25.

**SRV-17. Параллельные диалоги.** Долгий ответ в одной сессии не задерживает ответы в других. Реплики одной сессии обрабатываются строго по одной: вторая одновременная получает 409 `session_busy`. Число одновременных вызовов ядра ограничено `MAX_CONCURRENT_REQUESTS`; сверх предела — 503 `overloaded`, а не бесконечная очередь. (кейс, стр. 6, п. 6; ТЗ; предел — предложение; модель исполнения — Q-SRV-01)

**SRV-18. Таймауты и повторы.** Общий срок ответа на реплику — `CORE_TIMEOUT_S` (30 с по ТЗ); сервер передаёт его ядру как предельное время и по его истечении отвечает 504. Повторы выполняет только клиент моделей в ядре — ограниченное число с паузой при 429, 5xx и сетевом таймауте, и только если повтор укладывается в остаток срока (CORE-05); сервер вызов ядра не повторяет. Каждый сетевой вызов ядра имеет собственный таймаут, поэтому зависший вызов не занимает исполнителя дольше общего срока. Значения для пакетного прогона на платформе (таймаут генерации до 60–90 с) в чате не применяются. (ТЗ; регламент, §9; пример сабмита; CORE-05, CORE-13) Зависит от: CORE, Q-SRV-14.

**SRV-19. Поведение при недоступной модели.** При ошибке или таймауте модели клиент получает 502 или 504 в формате SRV-08; сессия остаётся рабочей — следующая реплика в ней обрабатывается, в истории нет «висящих» реплик; страницы истории и заявок продолжают открываться. Ответ с ошибкой не подменяется выдуманным текстом консультанта. (ТЗ; кейс, стр. 6, п. 6; стр. 10, п. 3)

**SRV-20. Источник моделей вне платформы.** Прокси организаторов доступен только внутри автопроверки (регламент, §6), поэтому на стенде и локально генерация, эмбеддинги и реранжирование подключаются через переменные SRV-04 к любому OpenAI-совместимому сервису; реранжирование отключается флагом. Проверенная комбинация «сервис — модель — переменные» записана в README. Для демо используется модель того же семейства, что на платформе, чтобы поведение совпадало. (кейс, стр. 8; стр. 9, п. 1) Зависит от: Q-SRV-10, Q-SRV-24.

**SRV-21. Сборка образа: фронтенд и сервер.** Образ собирается в несколько стадий: фронтенд из `web/` строго по lock-файлу, затем сервер с зависимостями фиксированных версий, ядро и собранная статика. Статика раздаётся с `/`, API — с `/api`, тем же сервером и портом; `index.html` отдаётся без кеширования; клиентские маршруты (история, заявки, `?embed=1`, `demo.html`) открываются по прямой ссылке. Сборке не нужны секреты; `.env`, `.git`, `data/` в контекст сборки не попадают. Образ собирается и работает на x86-64 и ARM64 (предложение, Q-SRV-27). Встраивание во фрейм не блокируется заголовками сервера или обратного прокси. (кейс, стр. 8; ТЗ) Зависит от: WEB.

**SRV-22. Сборка ZIP: полные проверки.** Сборщик кладёт в корень `solution.py`, `requirements.txt`, модули ядра и, если решено, файлы индекса, плюс манифест с идентификатором коммита. Сборка завершается ошибкой, если: есть `.py` во вложенной папке; размер больше 128 МБ; строка `requirements.txt` не совпадает с разрешённым набором с точностью до версии (эталон — файл организаторов из локального `data/`); в архиве есть `questions.csv`, `knowledge-base.zip`, `.env`, код сервера или фронтенда; найдены признаки ключей; в коде есть вызов установки пакетов; имя корневого модуля совпадает с модулем стандартной библиотеки или разрешённого пакета; рабочее дерево не закоммичено. Готовый ZIP лежит в `dist/` и в репозиторий не попадает. (регламент, §2, §4, §5; проверка имён и манифест — предложение) Зависит от: CORE (CORE-15), Q-SRV-08, Q-SRV-09, Q-SRV-18, Q-SRV-22.

**SRV-23. Локальная проверка ZIP.** Скрипт распаковывает архив в пустой каталог чистого контейнера, где установлены только зависимости из `requirements.txt` архива, с ограничениями 8 CPU и 16 ГБ; задаёт только переменные платформы (без наших дополнений); кладёт `questions.csv` и `knowledge-base.zip` в `DATA_DIR` из локального каталога вне репозитория; запускает `solution.py` с жёстким пределом 20 минут. После запуска проверяет `submission.csv`: лежит в рабочем каталоге, UTF-8, заголовок ровно `id,answer`, набор ID совпадает с входным, повторов нет, ответы непустые и не длиннее 10 000 символов, файл читается стандартным CSV-разбором. Набор вопросов содержит одиночные, диалоговые и многострочные случаи. Отчёт показывает время на вопрос и сколько вопросов уместится в 20 минут. Отдельный прогон с недоступной моделью подтверждает, что файл всё равно полон. (регламент, §3–5, §9; ТЗ; режимы — Q-SRV-05) Зависит от: CORE, Q-SRV-20, Q-SRV-21, Q-SRV-23.

**SRV-24. Первый сабмит и учёт попыток.** На платформу уходит только ZIP, прошедший SRV-22 и SRV-23. Каждая отправка записана в журнале сабмитов Ивана `core/docs/submits.md` (CORE-25) с идентификатором коммита из манифеста архива. Первый сабмит с баллом выше 0 получен на этапе 2. (кейс, стр. 11; регламент, §5; ТЗ) Зависит от: CORE, Q-SRV-18.

**SRV-25. Стенд с HTTPS.** Публичный адрес отдаёт интерфейс и API по HTTPS с действительным сертификатом, HTTP перенаправляется на HTTPS. Конфигурация стенда лежит в `deploy/` и не усложняет корневой `compose.yaml`: жюри локально не нужны домен и сертификат. Развёртывание описано в `deploy/` и повторяется на новом хосте. Ссылка передаётся Andrew для первого слайда. (кейс, стр. 8; ТЗ) Зависит от: Q-SRV-12.

**SRV-26. Защита истории, заявок и отладки на стенде.** При заданном `ADMIN_TOKEN` список сессий, заявки и отладочные данные с фрагментами базы знаний доступны только с кодом доступа; создание сессии и отправка реплик открыты. При пустом `ADMIN_TOKEN` (локальный запуск жюри) всё открыто, как требует проверка в прототипе. Чужую сессию нельзя прочитать перебором идентификаторов (SRV-09). Стенд запрещает индексацию поисковыми системами. Интерфейс предупреждает, что вводить можно только вымышленные данные. Переключатель реализуется в любом случае: решение команды определяет лишь его значение на стенде. (кейс, стр. 10, п. 1, 6, 8; предложение) Зависит от: Q-SRV-13, Q-SRV-26, WEB.

**SRV-27. Лимиты и защита бюджета.** На стенде ограничены: длина реплики, число реплик в сессии, частота запросов с одного адреса; превышение даёт 413 или 429. Суммарный расход на внешний API ограничен на стороне сервиса-поставщика или сервера, исчерпание лимита даёт понятную ошибку, а не зависание. Локально лимиты по умолчанию не мешают проверке сценария. (предложение; кейс, стр. 6, п. 6) Зависит от: Q-SRV-06.

## Этап 3. Качество

**SRV-28. История сессий «для проверки в прототипе».** Список сессий показывает все сессии с репликами — без заявки и с заявкой; сессий без реплик в списке нет. Поля: `session_id`, `started_at`, `messages_count`, `has_lead`, `lead_id`, `first_message`; сортировка от новых к старым, постраничная выдача. Полная история сессии содержит для каждого ответа бота `action`, `sources`, `debug` с разбивкой времени. История доступна через интерфейс, а не только через API. (кейс, стр. 6, п. 5 и 7; стр. 10, п. 6; ТЗ) Зависит от: WEB; пустые сессии — Q-SRV-02.

**SRV-29. Заявки и идемпотентность.** Заявка создаётся, когда ядро вернуло `lead_ready` с тремя заполненными полями и резюме по контракту 3. На сессию — не более одной заявки: повторный `lead_ready` обновляет запись и `updated_at`, второй записи не создаёт, в том числе при одновременных запросах. Заявка хранит ссылку на сессию; резюме сохраняется как пришло от ядра. (кейс, стр. 6, п. 4; стр. 10, п. 7; ТЗ) Зависит от: CORE.

**SRV-30. Валидация телефона.** В заявку попадает только номер в виде `+7` и 10 цифр. Нормализацию выполняет одна общая функция; сервер проверяет результат как инвариант. Если ядро вернуло `lead_ready` с номером, не прошедшим проверку, заявка не создаётся, случай пишется в журнал, а пользователь получает просьбу уточнить номер. (ТЗ; поведение при нарушении и допустимые форматы — Q-SRV-16) Зависит от: CORE.

**SRV-31. Передача заявки менеджеру (заглушка).** При создании заявки формируется событие с JSON заявки и резюме; при пустом `LEAD_WEBHOOK_URL` передача имитируется. Состояние передачи (статус, время, число попыток) хранится рядом с заявкой и видно в `GET /api/leads/{id}`. Событие создаётся один раз на создание заявки и отдельно на её изменение, с идентификатором заявки как ключом идемпотентности. Сбой передачи не ломает ответ пользователю. Тексты сервера и интерфейса не обещают срок звонка и имя специалиста. (кейс, стр. 6, п. 8; стр. 10, п. 7; ТЗ; база знаний, файл `00-reference/03-calculation-and-requests.md`; способ — Q-SRV-03)

**SRV-32. Журналирование.** Каждая обработанная реплика даёт строку журнала с `request_id`, идентификатором сессии, `action`, кодом ответа и временем по шагам. В журнал не попадают ключи, заголовки авторизации, ФИО, телефоны и тексты базы знаний. (регламент, §6; кейс, стр. 10, п. 1, 8, 9; предложение)

**SRV-33. Безопасность образа и зависимостей.** Все зависимости сервера и фронтенда зафиксированы по версиям; процесс в контейнере работает не от root; в слоях образа нет `.env`, ключей и каталога `.git`; известные уязвимости зависимостей проверены сканером, результат отражён в README. (кейс, стр. 8; стр. 12 — критерий «Безопасность, зависимости и документация»; предложение)

**SRV-34. Линт и автотесты сервера.** `make -C server lint` и `make -C server test` выполняют настоящие проверки и проходят в CI без сети, ключей и данных кейса. Тесты на тестовом двойнике ядра покрывают: все эндпоинты, все коды ошибок, изоляцию сессий, идемпотентность реплики и заявки, таймаут, параллельные диалоги, сохранность после перезапуска. Тестовые данные — только вымышленные. (правила, D-2; кейс, стр. 10, п. 8)

**SRV-35. Устойчивость стенда и план на случай падения.** Сервис сам поднимается после сбоя процесса и перезагрузки хоста; данные сохраняются. Внешняя проверка `/api/health` уведомляет команду о недоступности. Есть резервная копия хранилища и инструкция восстановления на новом хосте. В окно экспертной проверки выкатываются только исправления. Опорный способ проверки — локальный запуск одной командой: README и первый слайд говорят это прямо, поэтому падение стенда или исчерпание ключа не лишает жюри возможности пройти сценарий; в презентации есть снимки сценария. (кейс, стр. 8, стр. 11; предложение) Зависит от: Q-SRV-12, Q-SRV-27, WEB.

## Этап 4. Сдача

**SRV-36. README.md.** Содержит всё по списку кейса: назначение и архитектура; одна команда запуска через Docker; переменные окружения; порты; зависимости; порядок проверки основного сценария от первого вопроса до заявки; известные ограничения; для внешнего API — сервис, модель, имя переменной и порядок подключения ключа. В README нет действующих ключей, цитат базы знаний и реальных персональных данных. (кейс, стр. 8; дополнения — предложение) Зависит от: Q-SRV-07, Q-SRV-10, Q-SRV-25.

**SRV-37. Сценарий внедрения.** Документ `docs/integration.md` объёмом до одной страницы: как чат встраивается в сайт (тег скрипта и фрейм, реализация Andrew); как заявка попадает менеджеру (событие, схема JSON с резюме, ключ идемпотентности, повторы доставки); что в прототипе является заглушкой; что потребуется для боевого внедрения — в частности согласие на обработку персональных данных на шаге передачи контактов, как это устроено в действующем процессе согласно базе знаний, и разграничение доступа к заявкам. Примеры — только с вымышленными данными. (кейс, стр. 6, п. 8; стр. 12 — «Сценарий внедрения»; ТЗ; база знаний; Q-SRV-19) Зависит от: WEB.

**SRV-38. Проверка с чистой машины.** На машине без кеша Docker и без следов проекта человек, не занимавшийся инфраструктурой, по одному README клонирует репозиторий, выполняет описанные шаги и одну команду и проходит сценарий до заявки. Найденные расхождения исправляются в README, а не объясняются устно. (кейс, стр. 8, стр. 11; ТЗ)

**SRV-39. Комплект материалов и доступ жюри.** В репозитории или архиве есть: исходный код, `README.md`, `Dockerfile`, `compose.yaml`, `.dockerignore`, файлы зависимостей с фиксированными версиями, `.env.example` без действующих ключей, презентация PDF (вместе с ней — порядок проверки и ссылка на репозиторий для первого слайда). Если репозиторий приватный, аккаунту `hack-and-change-2026` выдан доступ и это проверено. (кейс, стр. 8, стр. 11) Зависит от: Q-SRV-07, Q-SRV-17.

**SRV-40. Финальная проверка утечек и данных стенда.** Перед сдачей проверка SRV-03 проходит по всей истории коммитов; в хранилище стенда только вымышленные ФИО, телефоны и компании; ни в одном материале, включая презентацию и снимки экрана, нет ключей. (кейс, стр. 8; стр. 10, п. 1, 8, 9)

**SRV-41. Финальный сабмит и заморозка.** Последний сабмит собран из коммита, который лежит в основной ветке; повторная сборка из этого коммита даёт архив с тем же списком файлов и теми же контрольными суммами. За сутки до дедлайна код заморожен: после этого — только исправления ошибок, README и презентация. (ТЗ; регламент, §5) Зависит от: Q-SRV-18, Q-SRV-27.
