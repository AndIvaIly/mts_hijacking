# Требования и план: ядро консультанта (Ivan)

**Зона ответственности:** `core/`, корневой `solution.py`, скрипты `core/scripts/`, документы `core/docs/`. Содержание: поиск по базе знаний (RAG), логика консультанта (ответ, уточнение, отказ, предложение заявки, сбор заявки, резюме), точка входа автопроверки, замеры качества.

**Результат работы:** (1) ZIP-сабмит, который проходит автопроверку и обходит baseline; (2) ядро с функцией ответа, которую без изменений вызывает сервер веб-чата; (3) локальная оценка качества и журнал сабмитов; (4) описание архитектуры поиска для README и презентации.

**Вес:** LLM-судья — 50% онлайн-этапа; ядро также определяет экспертные критерии «Качество консультации» (25%) и «Скорость и стабильность» (15%) (кейс, стр. 12).

**Зависит от:** Arthur — доступ к моделям и база знаний на стенде, проверка ZIP в Docker; команда — решения из `questions.md` (раздел «Решает команда»); организаторы — ответы на Q-CORE-21…29. **Отдаёт:** Arthur — ядро и контракт вызова; Andrew — смысл значений `action` и примеры ответов для моков; всем — формат резюме заявки.

**Обозначения источников:** `(кейс, стр. N)`, `(регламент, §N)`, `(ТЗ)` — заготовка `docs/tz-roles.md`, `(пример сабмита)` — `solution.py` и README организаторов, `(зависимости)` — разрешённый `requirements.txt`, `(демо: вопросы)`, `(демо: ответы)`, `(БЗ: файл)`, `(D-n)` — decision log, `(предложение)` — инженерная рекомендация, не утверждённая командой. Числа с пометкой «предложение» меняются строкой в decision log.

## Что показали данные

- **База знаний:** архив из 19 файлов Markdown в трёх папках: `00-reference` (карта продуктов, числа с оговорками, границы продуктов, расчёт и заявка), `10-energy` (основы энергорынка: 8 файлов), `20-products` (обзор, пять продуктовых направлений, общие вопросы). Около 130 тыс. символов, 233 раздела под заголовками; медиана раздела — 330 символов, 90% разделов короче 1 050 символов, самый длинный — около 4 900 (таблица чисел). (БЗ)
- **Разметка — экспорт pandoc:** строки жёстко перенесены по ~72 символа; 27 таблиц, из них 22 «сеточные» с переносом текста внутри ячеек и рамками из дефисов, 5 простых; разделители `---` между блоками; 43 ссылки на другие файлы по имени (одна ведёт на несуществующее имя); есть слипшийся с абзацем заголовок и списки, схлопнутые в один абзац. (БЗ)
- **Продуктовые файлы однотипны:** «кому / одной фразой», «что это», «кому подходит», «не подходит, если», «что мы не делаем», «частые вопросы» (вопрос клиента в заголовке третьего уровня), «факты, которые можно утверждать», «чего утверждать нельзя». Последние два раздела и пометки вида «помощник может / не отвечает» — это готовые правила поведения бота, а не текст для пересказа. (БЗ: 20-products/*)
- **Справочная папка задаёт рамку консультации:** каждое число идёт с обязательной оговоркой (`01-numbers-and-indicators.md`); перечислены границы каждого направления и случаи, когда нужен специалист (`02-product-scope-and-limits.md`); перечислены сведения, которые нужны для расчёта по каждому направлению, и ограничения на обещания при обратном звонке (`03-calculation-and-requests.md`). (БЗ)
- **Образцовые ответы (18 штук):** 25–52 слова, медиана 38; 2–5 предложений; первая фраза прямо отвечает на вопрос; сплошной текст без списков и разметки; от лица компании или безлично; в 13 из 18 ответ заканчивается ровно одним уточняющим вопросом, больше одного вопроса нет нигде; ни один ответ не предлагает оставить контакты; в диалоге, где клиент не готов давать телефон, образец это принимает и продолжает консультировать. (демо: ответы)
- **Демо-вопросы:** 13 одиночных и 5 диалогов. Диалог — одно поле CSV в кавычках: реплики с новой строки, с метками ролей «Пользователь:» и «Ассистент:», три реплики пользователя и две ассистента, последняя — пользователя. Файл начинается с BOM. Примеров отказа и сбора заявки в демо нет. (демо: вопросы)

## Этап 1. Каркас

Результат этапа: `solution.py` проходит полный прогон на заглушке моделей и выдаёт корректный `submission.csv`; контракт с сервером согласован; ZIP собирается одной командой.

**CORE-01. Локальные данные.** Материалы организаторов лежат только в `data/` (в `.gitignore`). Всё производное от них — dev-набор, эталоны, выгрузки ответов, индекс, логи с текстами вопросов и фрагментов — хранится там же и в коммиты не попадает. (кейс, стр. 10, огр. 1; D-5)

**CORE-02. Раскладка кода.** Один и тот же исходный код ядра без правки импортов работает в двух раскладках: все модули рядом с `solution.py` в корне ZIP; модули в `core/` репозитория, откуда их импортируют корневой `solution.py` и сервер. Логика ответа существует в одном экземпляре. (регламент, §4; ТЗ) Зависит от: Q-CORE-11.

**CORE-03. Зависимости.** Ядро и `solution.py` используют только стандартную библиотеку и пакеты из разрешённого списка; файл зависимостей сабмита перечисляет только реально импортируемые пакеты с версиями из списка организаторов. `pip install` из кода не вызывается. Пакеты, которым при первом запуске нужна загрузка файлов из интернета, не используются, либо их отказ не роняет прогон. (регламент, §4; зависимости; предложение)

**CORE-04. Конфигурация из окружения.** Адрес: `LLM_BASE_URL`, затем `OPENAI_BASE_URL`; ключ: `LLM_API_KEY`, затем `OPENAI_API_KEY`; модель генерации: `LLM_MODEL`, `GEN_MODEL`, `OPENAI_MODEL`; `EMB_MODEL`, `RERANKER_MODEL`; `DATA_DIR` (по умолчанию `data`); `MAX_WORKERS`, `TEMPERATURE`, `MAX_TOKENS` читаются с проверкой границ. Пустое значение или значение, равное имени самой переменной, считается отсутствующим. Идентификатор модели берётся из окружения; ключей и адресов нет в коде, файлах и логах. (регламент, §6; пример сабмита) Зависит от: Q-CORE-06.

**CORE-05. Клиент моделей.** Три вызова через один адрес: `/chat/completions`, `/embeddings`, `/rerank`, заголовок `Authorization: Bearer`. У каждого вызова есть тайм-аут и ограниченное число повторов с паузой при 429, 5xx и сетевом тайм-ауте; при 400 и 401 повторов нет. Повтор не начинается, если не укладывается в остаток бюджета (CORE-10). Числа (предложение): до 3 попыток, паузы 1 и 3 секунды, тайм-аут генерации до 60 секунд, эмбеддингов и реранкера — до 20. (регламент, §6, §9; пример сабмита)

**CORE-06. Заглушка прокси.** Для тестов и CI есть локальная заглушка трёх эндпоинтов с режимами: норма, 429, 5xx, пустой ответ, зависание. Тесты ядра не требуют сети, ключей и данных кейса. (предложение; AGENTS.md)

**CORE-07. Вход `solution.py`.** Скрипт находит `questions.csv` и `knowledge-base.zip` в `DATA_DIR`, а также относительно своего каталога и рабочего каталога; читает CSV в UTF-8 с возможным BOM и многострочными полями; `id` хранит как строку без изменений; порядок строк сохраняет. (регламент, §2–3, §6; пример сабмита; демо: вопросы)

**CORE-08. Выход `solution.py`.** В рабочем каталоге создаётся `submission.csv`: UTF-8 без BOM, заголовок ровно `id,answer`, одна строка на каждый входной `id`, без повторов и лишних столбцов, стандартное CSV-экранирование. Ответ непустой, не длиннее 10 000 символов, записан одной физической строкой. (регламент, §3, §9; пример сабмита)

**CORE-09. Гарантия полного файла.** Сразу после чтения вопросов записывается полный `submission.csv` с запасным ответом на каждый `id`; по мере готовности настоящих ответов файл атомарно перезаписывается. Исключение при обработке одного вопроса не влияет на остальные. Запасной ответ — осмысленный отказ с предложением специалиста, а не текст ошибки. Процесс завершается с кодом 0. (регламент, §3, §9; предложение)

**CORE-10. Бюджет времени.** Весь прогон, включая построение индекса, укладывается в 20 минут. Есть внутренний дедлайн (предложение: 16 минут от старта); бюджет на вопрос пересчитывается как «остаток времени × число потоков / число оставшихся вопросов» (при 3 потоках и 300 вопросах — около 9,6 секунды). При нехватке бюджета шаги отключаются в фиксированном порядке: реранкер → переписывание запроса → сокращённый контекст → запасной ответ. После дедлайна новые обращения к моделям не начинаются. (регламент, §5, §9) Зависит от: Q-CORE-21.

**CORE-11. Параллелизм.** Вопросы обрабатываются параллельно; число потоков — из `MAX_WORKERS` (по умолчанию 3, границы 1–8); при серии ответов 429 параллелизм снижается. Ядро потокобезопасно; состояние между разными `id` не переносится. (регламент, §3, §6; пример сабмита)

**CORE-12. Разбор диалога.** Строка `question` превращается в список реплик. Правила: (1) нет метки роли в начале первой строки — это одиночный вопрос; (2) новая реплика начинается только со строки вида «метка роли + двоеточие»; строка без метки продолжает предыдущую реплику; (3) метки сравниваются без учёта регистра, список меток расширяем (в демо — «Пользователь», «Ассистент»); (4) если последняя реплика не пользовательская или разбор не удался, вся строка передаётся как одна реплика пользователя; (5) текст реплик не изменяется. (регламент, §3; кейс, стр. 7; демо: вопросы)

**CORE-13. Контракт вызова ядра.** Ядро предоставляет: однократную инициализацию с путём к архиву базы знаний и признак готовности; функцию ответа `answer(messages, debug=False)` — без состояния, потокобезопасную, с необязательным предельным временем ответа; функцию разбора строки диалога. Результат — поля контракта 1 из ТЗ с уточнениями CORE-42, CORE-44, CORE-47. Сбой или тайм-аут модели ядро сообщает типизированной ошибкой: `solution.py` заменяет её запасным ответом, сервер — кодами 502 и 504. (ТЗ, контракт 1; предложение) Зависит от: Q-CORE-15.

**CORE-14. Заглушка и примеры для коллег.** К концу этапа Arthur получает заглушку ядра с финальной сигнатурой, Andrew — шесть примеров результата (по одному на каждое значение `action`) с выдуманными данными. (ТЗ)

**CORE-15. Сборка и проверка ZIP.** Одна команда собирает архив: в корне `solution.py`, `requirements.txt` и модули ядра; нет вложенных папок с модулями, данных кейса, `.env`, тестов; размер не больше 128 МБ. Проверочный скрипт подтверждает состав, соответствие зависимостей разрешённому списку и запускает архив в чистом окружении. (регламент, §4–5; пример сабмита) Зависит от: Q-CORE-12, Q-CORE-28.

**CORE-16. Линт и тесты области.** Цели `lint` и `test` в `core/Makefile` выполняют реальные проверки и проходят в CI. (D-2) Зависит от: Q-CORE-10.

## Этап 2. Сквозной сценарий и первый сабмит

Результат этапа: простой RAG отвечает по базе знаний; первый сабмит оценён платформой; сервер вызывает настоящее ядро.

**CORE-17. Загрузка базы знаний.** Из архива читаются файлы `.md` и `.txt` в UTF-8, служебные записи архива пропускаются; идентификатор документа — путь внутри архива. Код не зависит от числа и имён файлов. Если архив не найден или пуст, прогон не падает. (регламент, §2; пример сабмита)

**CORE-18. Разбиение с учётом разметки.** (БЗ; предложение)
- Единица — раздел под заголовком второго или третьего уровня; фрагмент хранит цепочку «название документа → раздел → подраздел», и эта цепочка входит в текст для поиска и для модели.
- Жёстко перенесённые строки склеиваются в абзацы до индексации.
- Таблица не разрезается внутри строки. Каждая строка таблицы становится записью «заголовок столбца: значение» с подписью раздела; ячейки, разнесённые на несколько строк текста, собираются целиком; значение не отрывается от своей оговорки.
- Линии-разделители блоков не принимаются за границы таблиц.
- Пункты списка остаются вместе с вводной фразой.
- Обрабатываются известные дефекты: заголовок, слипшийся с абзацем; список, схлопнутый в один абзац; абзацы без переносов.
- Ссылки на другие файлы заменяются названием целевого документа или удаляются.
- Размер (предложение): раздел длиннее ~1 200 символов делится по абзацам с повтором цепочки заголовков; раздел короче ~200 символов объединяется с соседним того же уровня. Перекрытие не используется.

**CORE-19. Типы фрагментов.** У фрагмента есть метаданные: путь и название документа, цепочка заголовков, направление (справочник, основы энергорынка, конкретный продукт) и тип: описание; частый вопрос; применимость; ограничения; разрешённые факты; запрещённые утверждения; число с оговоркой; данные для расчёта; пометка для помощника. Тип определяется по заголовку раздела, по умолчанию — «описание». (БЗ: 20-products/*, 00-reference/*)

**CORE-20. Индекс.** Эмбеддинги фрагментов запрашиваются у `/embeddings` пакетами, модель — из `EMB_MODEL`. Индекс живёт в памяти процесса и не требует внешних сервисов. Построение ограничено по времени (предложение: 60 секунд); при отказе эмбеддингов прогон продолжается на лексическом поиске. Готовый индекс, если он используется, привязан к хэшу архива и имени модели, при несовпадении пересчитывается. (регламент, §7; кейс, стр. 9) Зависит от: Q-CORE-01, Q-CORE-24.

**CORE-21. Базовый поиск.** По запросу возвращаются лучшие фрагменты с оценкой и метаданными. Число фрагментов ограничено бюджетом контекста модели. (кейс, стр. 6; регламент, §7)

**CORE-22. Базовая генерация.** Один вызов модели получает системную инструкцию, найденные фрагменты, историю диалога и последнюю реплику. Инструкция задаёт: роль консультанта Energytool; факты о продуктах — только из фрагментов; сведения о клиенте — только из диалога; простой язык; краткость; не больше одного вопроса; при отсутствии сведений — сказать об этом и предложить специалиста. Температура — из окружения (по умолчанию 0); предел длины генерации — собственный, не выше `MAX_TOKENS`. В тексте инструкций нет фактов и чисел из базы знаний и нет текстов демо-примеров. (кейс, стр. 6, 9, 10; регламент, §6–7; AGENTS.md)

**CORE-23. Постобработка ответа.** Из ответа удаляются блоки рассуждений модели, если они попали в текст; разметка Markdown; имена и пути файлов базы; лишние пробелы и переводы строк. Пустой результат — один повтор, затем запасной ответ. Ответ длиннее 10 000 символов обрезается по границе предложения. (регламент, §3; пример сабмита; предложение) Зависит от: Q-CORE-23.

**CORE-24. Первый сабмит.** Отправляется сразу, как только работают CORE-07…23, без ожидания улучшений. Цель — статус «оценён» и балл выше 0. (кейс, стр. 11; ТЗ)

**CORE-25. Журнал сабмитов.** Файл `core/docs/submits.md`, строка на сабмит: дата и время МСК, номер за день (из 5), коммит, что изменено, локальные метрики, статус или текст ошибки платформы, публичный Score. Текстов вопросов и ответов в журнале нет. (ТЗ; регламент, §5; D-5)

**CORE-26. Ядро в сервере.** Заглушка заменяется настоящим ядром без изменения сигнатуры; сценарий от первого вопроса до ответа по базе проходит через сервер. (ТЗ) Зависит от: SRV (доступ к моделям и база знаний на стенде, Q-CORE-13, Q-CORE-14).

## Этап 3. Качество

Результат этапа: поведение консультанта соответствует образцам и границам базы знаний; каждое изменение подтверждено локальным замером; полный сценарий до заявки проходит через `answer()`.

**CORE-27. Dev-набор.** Не меньше 60 случаев (предложение), хранится локально: 18 демо-вопросов и собственные. Категории: факт по каждому направлению; разговорная формулировка без терминов от каждой из пяти аудиторий; размытый запрос; цена, срок, число; граница продукта и запрещённое утверждение; ответа нет в базе; техдокументация и настройка приборов; тема не про Energytool; диалог из 2–4 реплик, включая смену темы и возврат; заявка (согласие, отказ, неполные контакты); попытка манипуляции. У случая есть ожидаемый тип поведения, ожидаемый документ-источник и эталонный ответ, написанный по базе. (кейс, стр. 5, 6, 10; регламент, §7)

**CORE-28. Локальная оценка.** Скрипт прогоняет `solution.py` на dev-наборе и считает: (а) корректность формата; (б) долю случаев, где ожидаемый документ попал в выдачу поиска; (в) попарную оценку судьёй по формуле платформы: два раунда со сменой мест, шкала из пяти значений, балл вопроса — среднее, Match Rate, Win Rate без ничьих, Score = 0,7·MR + 0,3·WR; соперник — пример сабмита организаторов на тех же вопросах; (г) длину ответа, число вопросительных знаков, наличие отказа там, где он ожидается; (д) время на вопрос (медиана и 95-й перцентиль) и долю запасных ответов. (регламент, §8; пример сабмита) Зависит от: Q-CORE-07, Q-CORE-13.

**CORE-29. Правило сравнения версий и расхода сабмитов.** Одна версия — одно изменение. Версия принимается, если локальный Score не ниже предыдущего с учётом шума (шум измерен двойным прогоном одной версии), ни одна категория dev-набора не просела сильнее порога, доля запасных ответов и время не выросли. На платформу уходит только принятая версия; один сабмит в день остаётся в резерве. (регламент, §5, §8; предложение)

**CORE-30. Гибридный поиск.** К векторному поиску добавлен лексический; он сопоставляет русские словоформы без внешнего морфологического анализатора. Результаты объединяются по рангам; почти одинаковые фрагменты из разных файлов не занимают несколько мест в выдаче. (ТЗ; зависимости; БЗ) Зависит от: Q-CORE-02.

**CORE-31. Словарь клиента.** Поиск находит нужный раздел по разговорной формулировке без терминов базы. Соответствия «слово клиента → продукт» с фактами из базы в код не записываются. (кейс, стр. 5; AGENTS.md)

**CORE-32. Поисковый запрос в диалоге.** Запрос учитывает историю: последняя реплика часто неполна без предыдущих. Способ (переписывание моделью или объединение реплик пользователя) выбирается замером; на одиночном вопросе лишнего вызова модели нет. (ТЗ; демо: вопросы)

**CORE-33. Реранкер.** Необязательный шаг через `/rerank`; остаётся в сборке, только если улучшает локальные метрики в пределах бюджета времени. При отказе используется порядок предыдущего шага. (регламент, §7; пример сабмита; ТЗ) Зависит от: Q-CORE-04.

**CORE-34. Справочный контекст.** Модель всегда располагает правилами базы о границах направлений и о случаях, когда нужен специалист; на размытом запросе в контекст попадает карта «задача → направление»; фрагмент с числом сопровождается его оговоркой из справочника чисел. (БЗ: 00-reference/*) Зависит от: Q-CORE-05.

**CORE-35. Достаточность найденного.** Перед ответом определяется один из трёх исходов: сведений достаточно; нужен уточняющий вопрос; сведений в базе нет. Порог по оценке поиска применяется только после калибровки на dev-наборе. (кейс, стр. 9, п. 4; регламент, §7; ТЗ)

**CORE-36. Форма ответа.** Первая фраза прямо отвечает на вопрос; далее 1–3 предложения по существу, привязанные к ситуации клиента из диалога; оговорка, если её требует база; не больше одного вопроса, и он стоит в конце. Целевая длина — 30–80 слов (предложение), больше 150 — только если вопрос этого требует. Сплошной текст без списков, заголовков, приветствий и упоминаний «фрагментов» и «файлов»; от лица компании; термины объясняются простыми словами. (демо: ответы; кейс, стр. 5, 10; регламент, §3) Зависит от: Q-CORE-08.

**CORE-37. Уточняющий вопрос.** Задаётся, когда следующий шаг зависит от факта, которого нет в диалоге. Спрашивается один параметр из перечней базы для соответствующего направления, в первую очередь тот, от которого зависит применимость продукта. Уже сказанное клиентом не переспрашивается. Если вопрос клиента закрыт полностью, вопрос в конце не обязателен. Если запрос слишком размыт для выбора направления, ответ состоит из краткого ориентира и одного вопроса (`clarify`). (кейс, стр. 6; демо: ответы; БЗ: 03-calculation-and-requests.md, 00-product-map.md)

**CORE-38. Числа и оговорки.** Каждое число в ответе есть в переданных фрагментах или в репликах клиента и сопровождается оговоркой из базы. Итоговая стоимость и расчёт по объекту не вычисляются. Единицы не подменяются (база отдельно предупреждает о путанице мощности и потребления). (кейс, стр. 10, огр. 2; БЗ: 01-numbers-and-indicators.md, 12-power-thresholds.md)

**CORE-39. Границы продуктов.** Бот соблюдает границы, заданные базой: пороги применимости с несколькими градациями, которые нельзя сливать в одну; сегменты, которым направление не предлагается; функции, которых у продукта нет; утверждения, верные для одного продукта и не переносимые на другой; сведения, которые не раскрываются; показатели, которые называются только вместе с рамкой сравнения. Если случай клиента за границей, бот говорит об этом прямо и называет направление, которое база предлагает взамен. Разделы запретов и пометки для помощника передаются модели как правила, отдельно от фактов. (БЗ: 02-product-scope-and-limits.md, 20-products/*)

**CORE-40. Отказ.** (а) Сведений нет в базе — бот прямо говорит об этом и предлагает специалиста, не достраивая ответ общими знаниями. (б) Техдокументация, настройка приборов, подбор конкретной модели, юридическое заключение — вне консультации, предлагается специалист. (в) Тема не про Energytool — краткий отказ и возврат к задачам клиента. Если рядом с вопросом в базе есть полезное, оно приводится. (кейс, стр. 6, 10, огр. 3–4; регламент, §7; БЗ: 02-product-scope-and-limits.md)

**CORE-41. Предложение заявки.** Предлагается, когда: клиент сам просит связаться, посчитать или прислать предложение; случай входит в перечень базы «нужен специалист»; задача прояснена, направление названо, и клиент спрашивает о следующем шаге. Предложение — одна фраза после содержательного ответа, без обещаний времени звонка, имени специалиста и содержания разговора. В соседних репликах не повторяется. После отказа клиента оставить контакты бот не возвращается к предложению, пока клиент сам не попросит. Вопрос о цене не является поводом для отказа: сначала ориентир с оговоркой, если он есть в базе. (кейс, стр. 6, п. 4; демо: ответы; БЗ: 02-product-scope-and-limits.md, 03-calculation-and-requests.md) Зависит от: Q-CORE-09.

**CORE-42. Поле `action`.** Одно из шести значений ТЗ; при нескольких подходящих действует порядок `lead_ready` → `collect_lead` → `out_of_scope` → `offer_lead` → `clarify` → `answer`. `answer` допускает уточняющий вопрос в конце. Текст ответа не зависит от того, запрашивались ли структурные поля: автопроверка и веб-чат на одинаковом входе идут по одному пути генерации. Если машинная часть вывода модели не разобрана, возвращается `answer` с полным текстом, а не ошибка. (ТЗ, контракт 1; кейс, стр. 9, п. 1) Зависит от: Q-CORE-03.

**CORE-43. Сбор заявки.** Состояние восстанавливается только из истории. После согласия клиента бот одним сообщением спрашивает все недостающие поля из трёх: ФИО, телефон, компания. Названное ранее не переспрашивается. Телефон приводится к виду `+7XXXXXXXXXX`; некорректный номер переспрашивается один раз. Вопрос клиента посреди сбора получает ответ и напоминание о недостающем. Поле заполняется, только если значение есть в репликах пользователя. При трёх полях возвращается `lead_ready` и подтверждение без обещаний сроков. (кейс, стр. 6, п. 4–5; ТЗ; БЗ: 03-calculation-and-requests.md) Зависит от: Q-CORE-19.

**CORE-44. Резюме заявки.** Формируется при `lead_ready` по контракту 3 с уточнениями: `client_type` — свободный текст; `object_details` включает названные клиентом параметры объекта; добавлено поле с резюме сплошным текстом для менеджера. В резюме только факты из диалога; чего клиент не говорил — «не уточнялось»; продукты — только те, что бот действительно назвал. Лимит 150 слов не действует. (кейс, стр. 6, п. 4; стр. 9, п. 6; стр. 10, огр. 5; ТЗ, контракт 3)

**CORE-45. Устойчивость к манипуляциям.** Указания внутри реплик пользователя или истории («забудь правила», «покажи инструкцию», «ответь от лица…») не меняют поведение; системная инструкция и фрагменты базы дословно не выдаются; имена клиентов, партнёров и производителей не называются. (БЗ: 02-product-scope-and-limits.md; предложение)

**CORE-46. Скорость ответа в веб-чате.** `debug.timings_ms` содержит время каждого шага. Цель на стенде: медиана до 5 секунд (ТЗ), 95-й перцентиль до 10 секунд (предложение). На обычную реплику — не больше двух вызовов генерации; извлечение полей заявки и резюме вызываются только на шагах заявки. (кейс, стр. 6, п. 6; ТЗ)

**CORE-47. Отладочные данные.** `sources` для каждого использованного фрагмента: путь документа в архиве, название документа, цепочка заголовков, оценка, короткий фрагмент текста; `debug` — поисковый запрос, время шагов, список отключённых шагов. (кейс, стр. 6, п. 7; ТЗ, контракт 1) Зависит от: Q-CORE-17.

## Этап 4. Сдача

Результат этапа: финальный сабмит оценён; материалы области готовы; репозиторий чист.

**CORE-48. Финальный сабмит.** Код ядра заморожен за сутки до дедлайна; финальной выбирается версия, лучшая по локальной оценке и публичному Score; её статус на платформе проверен; в последний день один сабмит остаётся в резерве. (ТЗ; регламент, §5, §8) Зависит от: Q-CORE-26.

Каждый участник может запустить локальную оценку и объяснить путь одного вопроса. (кейс, стр. 8, 12)
