# Правила проекта

Правила обязательны для всех, кто меняет репозиторий: троих участников и их ИИ-агентов (Claude Code, Codex, Cursor и др.). `CLAUDE.md` подключает этот файл целиком — правим только здесь.

## Проект

ИИ-консультант для сайта МТС Energytool (хакатон Hack&Change 2026): чат-бот, который по базе знаний подбирает клиенту продукт, задаёт уточняющие вопросы и передаёт менеджеру заявку с резюме диалога. Сдаётся в двух видах: ZIP с `solution.py` для автопроверки LLM-судьёй и веб-чат, запускаемый одной командой Docker.

Стек и инфраструктура ещё не утверждены — открытые вопросы в [docs/team-questions.md](docs/team-questions.md). Пока вопрос не закрыт строкой в decision log, не выбирайте технологию молча: предложите вариант и запишите решение.

## Порядок работы

Каждое изменение проходит три шага в этом порядке:

1. **Строка в decision log.** Изменение несёт решение — сначала запишите его в [docs/decision-log.md](docs/decision-log.md), потом пишите код. Решение — это выбор технологии или зависимости, изменение контракта между областями, отступление от ТЗ или требований, изменение структуры репозитория или этих правил. Исправление опечатки или бага без выбора между вариантами строки не требует.
2. **Линт.** `make lint` должен пройти.
3. **Тесты.** `make test` должен пройти. Новое поведение приходит вместе с тестом.

Коммит без зелёных `make lint` и `make test` не делаем. Если проверка падает, чиним причину, а не отключаем проверку или тест.

## Decision log

- Файл: `docs/decision-log.md`. Одна строка — одно решение.
- Формат: `D-n | ГГГГ-ММ-ДД | автор | область | решение и причина одной строкой`.
- `n` — следующий номер по порядку. Автор — `Ivan`, `Arthur` или `Andrew` (агент пишет имя участника, на которого работает). Область — `team`, `core`, `server` или `web`.
- Принятые строки не редактируем и не удаляем. Решение изменилось — новая строка: «… заменяет D-4».
- Решение области `team` (стек, контракты, инфраструктура, правила) принимают трое; в pull request его подтверждают остальные участники.
- На решение ссылаемся по номеру: в коммите, pull request и комментарии к коду — `D-12`.

## Рабочие области

Все видят весь код, но менять можно только свою область. Карта — в [workspaces.toml](workspaces.toml):

| Участник | Область | Что в ней |
| --- | --- | --- |
| Ivan | `core/`, `solution.py` | Ядро консультанта: поиск по базе знаний, логика диалога, точка входа автопроверки |
| Arthur | `server/`, `deploy/`, `Dockerfile`, `compose.yaml`, `.dockerignore`, `.env.example` | API-сервер, хранение, Docker, деплой, сборка сабмита |
| Andrew | `web/` | Веб-чат, режим отладки, история, виджет |

Всё остальное — общая зона (`docs/`, `scripts/`, `.github/`, `README.md`, `Makefile`, `workspaces.toml`, эти правила): меняется через pull request с согласия остальных.

Правила для участника и для агента:

- Перед началом работы определите, на кого вы работаете: файл `.workspace-owner` в корне (создаётся командой `make setup OWNER=<ivan|arthur|andrew>`). Если файла нет — спросите человека, не угадывайте.
- Не создавайте, не меняйте и не удаляйте файлы в чужой области, даже если правка очевидна и «всего одна строка».
- Нужна правка в чужой области — не делайте её. Опишите владельцу, что и зачем нужно изменить: в pull request, issue или чате команды. Правку вносит владелец.
- Интерфейсы между областями (функция ядра, HTTP API, формат резюме заявки) описаны в [docs/tz-roles.md](docs/tz-roles.md) и уточняются в документах областей. Изменение контракта — решение области `team`.
- Планы и требования участника лежат в его области: `<область>/docs/requirements.md`, `acceptance.md`, `questions.md`. Работу сверяйте с ними.

Границы проверяют pre-commit-хук, CI на каждом pull request и ревью владельца по CODEOWNERS.

## Ветки и pull request

- Ветка: `<участник>/<тема>`, например `ivan/hybrid-search`. Общие изменения — `shared/<тема>`.
- В `main` — только через pull request; прямых пушей нет. `main` всегда запускается.
- Один pull request — одна область. Изменение, задевающее общую зону, ревьюят остальные участники.
- Перед pull request: строки решений добавлены, `make check` зелёный.

## Данные кейса и секреты

Репозиторий публичный, поэтому:

- Материалы организаторов (база знаний, вопросы, образцы ответов, регламент) лежат только локально в `data/`. В репозиторий не попадают ни сами файлы, ни их копии: дословные фрагменты базы знаний в коде, тестах, моках, индексе, документах и скриншотах.
- Ключи, токены и пароли — только в переменных окружения и локальном `.env`. В репозитории — `.env.example` с пустыми значениями.
- В тестах, моках и примерах — только выдуманные ФИО, телефоны и компании.
- Бот берёт факты о продуктах, ценах и условиях только из базы знаний; дописывать их в промпты и код «от себя» нельзя.

`make lint` блокирует типовые имена файлов с данными и строки, похожие на ключи. Это страховка, а не замена внимательности.

## Команды

```bash
make setup OWNER=ivan   # один раз после клонирования: назвать себя и подключить git-хуки
make lint               # decision log, запрещённые файлы, линтеры областей
make test               # тесты общих проверок и тесты областей
make check              # lint + test
make guard              # не задел ли я чужую область относительно origin/main
```

Линт и тесты области настраивает её владелец в `<область>/Makefile` (цели `lint` и `test`).
